## 0. 一句话现状

**AI 服务侧（P0/P1）已经做完并通过自测；但原计划定义的"整体 P0"还没达成 —— 因为主服务的 `remoteAIClient` 还没接上，所以现在这个服务其实"没人用"。**

打通主服务是唯一的阻塞项，优先级高于任何新功能。

## 2. 阶段 F：立即打通（阻塞项，必须先做）

> **目标**：让真实用户能用上派蒙。没有这一步，后面所有功能都是自娱自乐。

| # | 交付物 | 依赖 | 验收 |
| --- | --- | --- | --- |
| F1 | 主服务 `remoteAIClient` + `NewAIClient` 的 `remote` 分支 | 代码模板见 `03-主服务对接说明.md` | `ai.provider=remote` 时 `POST /api/chat` 返回真实派蒙回复 |
| F2 | 主服务 `AIConfig.TimeoutSeconds`（默认 65）+ 降级兜底 | F1 | 停掉 AI 服务后 `/api/chat` 返回 200 + 可读降级文案，不 500、不泄漏内部错误 |
| F3 | 建表 `ai_prompts` + 种子数据 | `db/migrations/001_ai_prompts.sql` | 表存在且 3 条场景数据到位 |
| F4 | 生产切换提示词来源：`PROMPT_STORE_MODE=file → http` | 主服务实现 `GET /internal/v1/ai/prompts`（`X-Internal-Key`） | 改 DB 里的提示词、等 60s TTL，AI 回复随之变化 |
| F5 | 端到端验收（§6 的 12 项清单） | F1~F4 | 全部通过，填入 `04-部署运维接入说明.md §12` |

**粗估**：F1+F2 ≈ 0.5~1 人天；F3 ≈ 0.5 天；F4 ≈ 1 天；F5 ≈ 0.5 天 → **合计 2.5~3 人天**

**并行**：F3/F4 需要主服务仓库改动，若与 F1 同人执行可顺路做。

## 3. 阶段 V：价值跃升（建议插在 RAG 之前）

> 这两个阶段都不需要新依赖、不需要 embedding，但直接决定"派蒙懂不懂我的号"。
> **产品价值高于 P2 向量 RAG，成本却低得多**，所以建议插队。

### V1 · 玩家数据注入闭环（模式 A：Push）

| # | 交付物 | 验收 |
| --- | --- | --- |
| V1.1 | `PlayerProfileProvider`：按 UID 取 Enka 档案，**带 TTL 缓存 + singleflight** | 同一 UID 连续提问不重复打 Enka |
| V1.2 | `buildAIContext`：分级注入（全角色概览 + 相关角色明细） | 30 个角色时上下文 ≤ 1500 tokens |
| V1.3 | 降级：拉档案失败不阻塞聊天 | 断开 Enka 后 `/api/chat` 仍正常回答（只是不知道你的角色） |
| V1.4 | 透传 `context` 到 AI 服务 | 实测派蒙能复述真实练度（已用真实请求验证过渲染链路） |

**粗估**：**1.5~2.5 人天**（主要成本在 Enka 客户端 + 缓存 + 筛选逻辑）
**参考**：AI 服务侧已就绪，`03-主服务对接说明.md §6` 有完整 Go 代码与 token 预算表。

### V2 · 结构化资产查表（替代大部分 RAG 需求）

| # | 交付物 | 验收 |
| --- | --- | --- |
| V2.1 | 命中角色名 → 查 `asset_character_stat_weights` → 拼入 `context.summary` | 问「胡桃推荐词条」能给出精确的 primary/secondary 分级 |
| V2.2 | 扩展 `asset_weapons` / `asset_relic_sets` 同理 | 问「护摩之刃适合谁」不再靠模型记忆 |
| V2.3 | 明确"资料外不编造"的兜底话术 | 问冷门/新角色时承认不知道，而非编数值 |

**为什么优先于向量 RAG**：

| | 需要 embedding | 需要向量库 | 准确率 |
| --- | --- | --- | --- |
| 结构化查表 | ❌ | ❌ | 100%（精确匹配） |
| 向量 RAG | ✅ 另找供应商 | ✅ | 取决于检索质量 |

**粗估**：**1~2 人天**

## 4. 阶段 P2：向量 RAG（攻略文本）

> **前置条件（缺一不可，未满足就不要开工）**：
> 1. 有**可持续获取的攻略语料**（授权/自建/合作，注意版权）
> 2. 定了 **embedding 供应商**（DeepSeek 不提供该能力，见 §9 决策点）

| # | 交付物 | 验收 |
| --- | --- | --- |
| P2.1 | 语料导入管线：Loader → 中文友好切分（`RecursiveCharacterTextSplitter`，chunk≈500/overlap≈80） | 能对样例语料建索引 |
| P2.2 | Embedding 接入 + 向量库（开发 Chroma，生产可选 Milvus/pgvector） | 索引可重建、可增量 |
| P2.3 | 检索链：MMR + topK + 相似度阈值（必要时加 rerank） | 命中准确率达标（自建 20~30 条评测集） |
| P2.4 | 拼入 system 动态区 + 填充 `data.sources` 引用来源 | 回答能标注来源；契约不破坏（`sources` 字段早已预留） |
| P2.5 | 检索质量回归集 | 每次调参可跑分，不退步 |

> ⚠️ **风险**：检索质量决定上限。召回错了，DeepSeek 拿着错资料照样答错（garbage in, garbage out）。
> 调参（切分粒度 / topK / 阈值 / rerank）花的时间通常比选 embedding 模型多得多。

**粗估**：**3~5 人天**（不含语料获取与清洗；语料工程往往是大头）

## 7. 机会点：多模态视觉（建议评估）

DeepSeek V4.1 Flash **原生支持视觉**（JPEG/PNG/GIF/WebP，`image_url` 部件）。

产品上可以做：**「截图发给派蒙，让它帮我看这件圣遗物值不值得留」**

| 侧 | 改动量 | 说明 |
| --- | --- | --- |
| AI 服务 | **很小（0.5~1 天）** | `content` 已是部件数组兼容结构，只需放开图片部件透传 |
| 主服务 | 中等 | 需要图片上传/存储链路 + 大小限制 |
| 前端 | 中等 | 图片选择/粘贴/预览 |

**粗估**：**1~2 人天（AI 服务侧）**，产品价值高，属于"投入产出比很好"的加分项。

## 9. 需要你拍板的决策点

| # | 决策 | 选项 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| D1 | 部署形态 | Docker / 裸机 systemd | 运维方式 | Docker（跨平台，和主服务同机不同容器） |
| D2 | 提示词来源 | `file` / `http` | 改提示词是否要发版 | 生产用 `http`（改 DB 即生效，符合"业务数据入库"规范） |
| D3 | **Embedding 供应商** | 本地 `bge-m3` / 第三方 API | 是否多一个密钥与配额 | ✅ **已定：百炼 `qwen3.7-text-embedding-flash`**（目标环境是阿里云，1024 维、OpenAI 兼容、零新依赖、成本 <1 元/月）。详见 `06-阿里云部署方案.md §3` |
| D4 | **攻略语料来源** | 自建 / 授权 / 合作 | **P2 能否开工** | ⬜ **仍未定，是 P2 的唯一阻塞项**；未定前先做 V2 结构化查表 |
| D5 | 向量库 | numpy / Chroma / Milvus / pgvector | 运维复杂度 | ✅ **已定：起步用 numpy**（语料 <1 万段暴力检索足够）；上万段后再考虑 RDS PostgreSQL + pgvector |
| D6 | 主子服务是否同机 | 同机 / 跨机 | `AI_SERVER_HOST` 与防火墙 | ✅ **已定：同机**（同一台 ECS 走 `127.0.0.1`，不配 8090 安全组规则，天然不暴露公网） |

## 10. 明确不做 / 不建议做

| 事项 | 原因 |
| --- | --- |
| ❌ AI 服务直连业务库（MySQL） | schema 变更会跨服务断裂，破坏"完全独立"；提示词走内部接口，资产走导出/查表 |
| ❌ AI 服务里做用户体系 / 会话持久化 | 职责在主服务；AI 服务必须无状态才能随意重启扩容 |
| ❌ 为了省钱换掉 DeepSeek | 成本大头是对话输出 token；embedding 是零头。换平台迁移成本 > 多管一个 key |
| ❌ 先做向量 RAG 再做结构化查表 | 顺序反了：查表零依赖、准确率 100%；RAG 要新供应商且依赖语料 |
| ❌ 同步链路叠加"重试 + 长超时" | 硬约束：重试 ≤1 次，总耗时有上限 |
| ❌ 用 `ALLOW_INSECURE_DEV=true` 绕过启动自检 | 等于 `/v1/*` 裸奔 |
| ⚠️ 引入 LangChain 的 Memory 类 | AI 服务无状态，会话归主服务；用了就破坏边界 |
| ⚠️ 把动态内容（时间戳/随机值）塞进人格提示词 | 会让 DeepSeek 前缀缓存整段失效，缓存命中价差 50 倍 |

## 11. 推荐执行顺序

```
[阻塞项]  F1 主服务 remote 对接 ──► F2 降级 ──► F5 端到端验收
                                              ▲
[并行]    F3 建表 ──► F4 提示词走 http ────────┘

[价值]    V1 玩家数据注入 ──► V2 结构化查表
              （做完这两步，派蒙「懂你的号 + 数值不幻觉」，产品就成型了）

[可选]    视觉截图分析（投入产出比高，可穿插）

[有前置]  P2 向量 RAG  ← 卡在 D3 Embedding 供应商 + D4 攻略语料
          P3 Agent/工具
          P4 可观测/成本/限流

[并行]    O1 Docker 构建实测
```

### 里程碑

| 里程碑 | 标志 | 内容 |
| --- | --- | --- |
| **M1 · 能用** | 真实用户能在前端和派蒙对话 | F1~F5 |
| **M2 · 懂你** | 派蒙能准确复述你的角色练度并给个性化建议 | V1 |
| **M3 · 可信** | 游戏数值类问题不再靠模型记忆，有据可依 | V2 |
| **M4 · 有据可查** | 攻略类问题能引用来源 | P2 |
| **M5 · 会动手** | 派蒙能自主调用工具多步分析 | P3 |
| **M6 · 可运营** | 能看到每用户成本、能限流熔断 | P4 |
